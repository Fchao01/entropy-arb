# 溢价 bps 开平仓策略

在网页配置中选择「溢价 bps 开平仓」，或 YAML 设置 `strategy.mode: bps`。不指定时继续使用旧套利阈值策略；保存配置不会自动启动任务。

新口径 `bps.price_basis: executable` 按主腿/对冲腿角色计算，适用于所有交易所组合：

| 持仓方向 | 开仓信号 | 平仓信号 |
| --- | --- | --- |
| 买主腿、卖对冲腿 | `(对冲腿买一 / 主腿卖一 - 1) × 10000` | `(主腿买一 / 对冲腿卖一 - 1) × 10000` |
| 卖主腿、买对冲腿 | `(主腿买一 / 对冲腿卖一 - 1) × 10000` | `(对冲腿买一 / 主腿卖一 - 1) × 10000` |

开仓和平仓均为信号 **≥ 各自门槛**。价差口径和成交方式分别配置：开仓尊重 `execution.primary_order_type` 的 maker/taker 选择，不因使用 executable 而覆盖成 taker。Arcus 主腿选择 maker 时，开仓、平仓和 Arcus 余仓修正均为 Post-only，不回退吃单；其它主腿的平仓及余仓修正规则保持原样。上述触发指标与历史分位数继续按双边买卖报价计算；maker 开平仓还会核验主腿挂单价与对冲腿深度的价差。只取达到门槛的盘口档位，数量仍受单笔金额、每腿持仓上限、最小规模和精度限制；大单不会因第一档达标就吃入不合格档位。订单滑点预算按本批报价到门槛的余量收紧；例外是 Arcus 主腿 maker + RH 对冲的已确认成交，对冲使用独立的 `execution.hedge_slippage_bps`，每次从最新 RH 最优价计算保护价，不再套用入场余量。RH 明确因滑点取消且零成交时不设重试次数上限，结果不明、暂停/停止、行情不可用或预算/限流限制时停止补单；其余路径保持原规则。部分成交、行情变化和真实费用仍可能导致实际结果偏离，门槛不是利润承诺。

Arcus 主腿 maker + RH 对冲的开仓和平仓数量还受 RH 滑点保护范围内深度乘已有 `sizing.take_fraction` 的上限约束，不足最低规模不挂单；提交前再次缩量，挂单期间深度不足会撤单重算。不会因此扩展原策略允许的价差档位、提高配置金额上限或改变开平仓点位。详见 [RH 深度缩量与补单](primary.md#arcus-挂单数量随-rh-深度缩小)。

`price_basis: mid` 保留旧版中间价判断，用于兼容。实时触发还需满足行情新鲜、订单预算、仓位限制与信号持续时间。

## 自动点位

```yaml
strategy:
  mode: bps
bps:
  price_basis: executable
  levels: rolling
  history_mode: records
  direction: long_primary
  window_minutes: 120
  min_valid_minutes: 30
  entry_percentile: 90
  exit_percentile: 75
  add_interval_sec: 60
  max_position_usd: 1000
```

参数为可修改的示例。默认 `history_mode: records`，每分钟从 YAML `recorder.csv` 中取最新 N 条有效分钟收盘买卖报价，N 沿用 `window_minutes` 字段，默认 120。允许记录不连续、跨时段，也允许使用本次启动前采集的历史。已有历史超过 120 条就直接用最新 120 条，不必重新采集或等待 120 分钟。

每条须至少 10 次有效采样；同一分钟的有效重复记录只计一次，未完成分钟、未来记录和无效值不参与计算。`min_valid_minutes` 默认 30，实际最低数量为 `min(N, min_valid_minutes)`；设置为 120 就要求 120 条有效历史，但不要求连续。旧版 `min_coverage_pct` 仅为兼容保留，不限制点位计算。

分别从开仓方向、平仓方向的历史可成交价差序列取分位数，示例为开仓第 90 分位、平仓第 75 分位；两者都是越高越偏向历史高价差，不要求两个独立门槛之间大小排序。已有 CSV 的四个买卖报价列可直接重算，不使用旧中间价点位，也不删除历史；旧 CSV 没有买卖报价时等待新记录，不用中间价冒充。历史没有档位数量，故历史点位只是盘口报价参考，实际数量另按实时深度核验。有效记录不足时不开新仓。读取在后台线程进行，记录尾部不足时扩大读取范围，不在盘口回调中扫描 CSV。页面显示最新历史参考范围和最后一条记录距今多久；历史可能跨越较长时间，点位不一定适合当前行情。已有持仓继续使用开仓时锁定的点位，后续更新供下一轮参考。

如需保留严格时间窗口，可显式设置 `history_mode: time`：只读取最近 N 分钟时间范围内的有效记录，允许缺口，但不使用窗口外数据补足数量。两种方式均直接复用已有 CSV，重启不清除历史、不重设采集起点，也不要求本次进程重新采集。

CSV 旁的 `.source.json` 记录主腿、对冲腿、市场名称及可用历史起点。没有来源记录的旧 CSV，以及上一版仅记录升级时间的来源记录，会按 YAML 指定路径复用历史，日志提示 `CSV legacy history reused`。这一兼容操作假定旧历史与当前 YAML 的交易所、市场及主/对冲腿方向一致；旧格式无法验证这一点，曾混用路径或对调主腿的历史应先分开存放。升级后的来源记录使用 version 2；此后已记录的交易所/市场或腿方向变化会保留新起点，不混用变化前的数据，也不删除原 CSV。来源记录损坏时拒绝使用，不自动猜测。

第一批成交后，本轮开仓点位和平仓点位固定。之后滚动计算的点位留给下一轮；允许加仓时仍按本轮点位判断。不再限制开仓批次数量，旧 YAML 的 `max_entries` 为兼容保留读取但不再生效；`max_position_usd` 是每条腿的总持仓上限，同时受原有两条腿各自的仓位上限和单笔下单上限约束。

## 手动点位

```yaml
strategy:
  mode: bps
bps:
  price_basis: executable
  levels: manual
  direction: long_primary
  entry_bps: 1
  exit_bps: 1
  max_position_usd: 1000
```

此时不使用滚动分位数，两个方向各自满足 ≥ 点位就可发单；示例仅说明配置格式。未指定 price_basis 的旧手动配置仍保持 mid，避免将旧负数点位误当作新门槛。切换时显式设置 executable 并重新填写两个独立点位。

## 成交和成本

executable 和 mid 两种口径的开仓都遵循主腿成交方式。配置 maker 时主腿发送 Post-only 订单，仅将已确认新增成交量在对冲腿吃单对冲；未成交不发送对冲订单。Arcus 主腿 maker 配置的平仓也先挂只减仓订单，再按实际成交量对冲；Arcus 修正订单只挂单减仓、不向另一腿发单。开仓、平仓和修正中实际采用挂单的 Arcus 成交均使用主腿 maker 费率。其它主腿的平仓、余仓修正继续使用 taker 费率。可用以下配置选择挂单：

```yaml
execution:
  primary_order_type: maker
  maker_cancel_policy: best_price
```

已被旧页面保存为 taker 的 YAML 需要在对应配置来源中重新选 maker 并保存，更新代码不会猜测哪些 taker 任务原本想使用 maker。网页的 BPS 挂单选项保持可选，监控分别显示开仓与平仓实际成交方式。

Arcus 只挂单策略不保证立即退出：条件失效或离开最优价时按规则撤单，未成交不会改发 IOC；修正后仍存在无法消除的敞口或订单结果未确认时暂停新订单并保留现场。停止程序会请求撤单并核对最后成交，不会主动吃单平仓。必须由用户核对交易所订单与持仓后处理未完成部分。

默认 `execution.maker_cancel_policy: best_price`：先检查本轮 BPS 开仓条件和双腿可交易状态，不满足就立即请求撤单；满足后，买单在买一、卖单在卖一（或报价优于最后公开最优价）持续保留，不设总等待上限。连续离开最优价达到 `execution.maker_reprice_delay_sec`（默认 0.3 秒）才撤单；期间回到最优价会重置确认计时。原阈值策略也先检查自身有效门槛，再判断最优价。信号、对冲深度、行情、订单预算或人工停止等取消条件优先于队列位置，不受离开最优价确认时间影响。

已挂订单按“原计划数量 − 已确认对冲量”检查剩余对冲风险，包含已成交但尚未对冲的数量。检查使用该订单的固定挂单价、当前合格对冲深度及真实剩余风险；不再重新套用新单的 `take_fraction` 或最小下单量。初次下单仍遵守这两项限制，已成交的微小切片仍按原逻辑累计、对冲或纠偏。实时价差不达标、合格深度不足、行情过期、仓位未确认等情况仍立即请求撤单。日志 `quote-invalid:<具体原因>` 与 `[MAKER CHECK]` 给出实时信号、目标、剩余挂单量、所需对冲量及深度，避免混成一个原因。

明确零成交结束后，默认至少间隔 `execution.maker_requote_delay_sec: 0.5` 秒才允许下一张策略挂单，并重新按 `premium_persist_sec` 确认信号；新单仍核对最新价格和深度。设为 `0` 可取消这一间隔。已经确认的成交对冲、余仓修正不等待此重挂间隔；不会在旧单最终状态未确认时另挂新单。

交易所返回 `MARGIN_CANCELED` 后，记录当时可用保证金、权益和仓位，暂缓增加该腿风险的策略订单；不再误标成限流并每 10 秒直接重试。余额轮询继续运行，至少 60 秒后获得可用保证金确实增加且为正的新快照时，自动解除该进程的开仓限制并重新判断信号。快照缺失时先建立真实基准。减仓及纠偏保留原有订单确认与只减仓规则。该处理不会凭余额推算未知杠杆或保证金要求，也没有增加跨进程资金预留或请求额度协调。

普通点位模式只剩已确认、不可单独下单的小额精度尾仓时，交易点位跟随当前历史更新；数量和成本台账不变，旧轮损益不宣告已实现。有效持仓及未知订单/仓位仍保留原规则。

零成交且无提交错误的挂单批次仍保留 CSV，Telegram 每 5 分钟有后续批次时汇总，不再逐条发送成交通知或记录 `BPS CYCLE complete`。真实成交、未知结果及提交错误仍单独通知，保证金取消单独告警。Telegram 429 完整遵循 `retry_after`；退出时最多额外等候通知 3 秒，未送达的任务取消，不影响已执行订单的确认流程。

撤单后先确认旧单终态并处理最后新增成交，才释放订单锁并重新评估下一单，不在旧单结果未知时重挂。主腿价格档位不代表精确排队名次，仍在卖一/买一也不保证成交。长时间保留时 Arcus 每 5 秒主动核验订单状态，查询不撤单、不重置排队；WS 与主动查询都无法确认时仍按原保护处理。

如需保留原来的固定超时撤单，可显式设置 `execution.maker_cancel_policy: timeout`，此时 `maker_timeout_sec` 控制最长等待，范围 (0, 60] 秒。最优价模式忽略此总等待时间；网页会隐藏该输入框并展示当前规则。升级时未指定策略的 maker 配置默认采用最优价保留模式。

BPS 点位平仓每一批都重新检查本轮锁定的平仓点位，满足才提交一批只减仓订单；Arcus 主腿 maker 配置继续先挂单，其它主腿按原成交方式执行，均遵循滑点保护和单笔上限。不满足就保留剩余配对仓位等待；若重新达到开仓点位，允许在持仓金额上限和原有加仓间隔内加仓。已有持仓数量配对、方向符合配置，且核验无未成交订单及仓位稳定后，可直接接管并使用当前 BPS 口径，不要求先平仓。切换口径时不沿用旧点位：手动模式使用当前配置，滚动模式直接用已有有效历史重算，再允许按点位加仓/平仓；规模和加仓间隔限制不变。已有已知成本保留，无法确认的历史成本标为未知；旧状态先归档。重启恢复的旧「平仓中」状态也不能绕过点位检查。已经发出的订单仍可能在价差回退后成交。每批平仓均须重新达到 BPS 点位，没有止盈、止损或最长持仓触发的连续退出。

已确认成交产生的净差额优先使用 reduce-only 减少多余的一腿。若多余的一腿因最小规模无法减仓，可在核验双方无挂单、实际仓位与成交台账一致后，使用 IOC 补齐缺少的一腿，仅沿配置的持仓方向增加，且不超过净差额。补齐遵守该腿的真实吃单最小规模、数量步长、盘口深度、单笔上限和每腿持仓上限；绝不向上凑到最小单量。Arcus 仅挂单主腿不会因这条后备路径改成吃单；无法合法补齐仍保留保护。行情、限流或下单预算暂不可用时优先等待减仓条件恢复。确认部分成交或零成交后，最多连续尝试三笔，仅处理剩余差额，并按最新盘口及原有滑点保护下单，未确认的对冲绝不重复发送。连续下单失败次数触发暂停时，仍先减仓处理本批已确认成交留下的差额，修正完成不自动解除该失败次数保护。

例如 Arcus 为 +0.7772325 SPY、RH 为 −0.7771 SPY，净差额 +0.0001325 SPY（约 $0.102），超过默认精度尾差范围；Arcus 的最小减仓量 0.001 SPY 使原减仓路径无法执行。新版核验订单与仓位后，尝试在 RH 补卖 0.0001 SPY，按实际成交计入数量、成本、成交额及配置手续费；如全部成交则净差额降为 +0.0000325 SPY（约 $0.025），满足精度与金额条件后恢复评估。未成交继续等待，结果未知暂停并核验，平台明确拒绝时保留原因。不会为了消除这约两美分尾差而额外开大单。日志 `[HEDGE] mode=top-up` / `mode=reduce-excess` 区分补齐与减仓，`[HEDGE SETTLED]` 显示实际成交量及修正后净差额。

运行中已确认的差额遇到行情过期、交易连接未就绪、下单预算不足，或本轮三笔修正均明确零成交/部分成交时，进入 `[BPS REPAIR WAIT]` 自动等待，阻止新的策略订单，约每 5 秒重评一次，不因短暂断线永久 HALTED。行情与连接恢复后，先等待最近成交的 REST 同步宽限期，锁住两腿并查询双方未成交订单和实际仓位；无挂单且与已确认成交台账一致，才减仓修正。查询失败、无效响应或尚有挂单继续等待，不凭行情恢复直接补单。修正期间保留锁定点位、真实仓位、成本和待完成批次，完成后只结算该批一次，并重新确认策略信号。Arcus 主腿仅挂单规则仍适用于修正。

低于最小下单量的尾差不会补到最小数量。须在恢复的新鲜双边报价下重新满足 `max_dust_notional_usd` 及数量限制，才能保留尾差并自动恢复策略；例如已确认净差额 −0.0000522 SPY、名义敞口约 $0.04，断线时先等待，恢复并核验通过后保持精确数量继续运行。日志 `[BPS REPAIR RESUMED]` 表示本次核验/修正完成。实际仓位与台账不一致、订单结果未知、修正单明确失败或无法下单且超过尾差容忍范围，仍保留保护暂停；不会删除状态文件或自动解除人工暂停/连续失败保护。等待状态也保存 `pending`，进程重启后仍走严格的旧订单与仓位核验流程。

更新代码后，需要停止并重新启动对应的策略任务，已经运行的 Python 策略进程不会自动重载源码。`[BPS EXIT POLICY] levels-only` 可确认已加载纯 BPS 点位模式。新版 BPS 启动日志的 `[BPS REPAIR POLICY]` 包含 `fallback=verified-deficient-leg-top-up`，用来核对是否加载了减仓与补齐逻辑。旧版已 HALTED 的任务重启后会先按旧 pending 恢复流程核验；保留原状态文件和配对仓位，无须手工删文件。正尾差落在 Arcus、另一腿 RH 行情断开的情况也走自动等待。

RH/LIGHTER 的 reduce-only 吃单允许从一个数量步长开始，不能套用普通 maker 的最小数量与金额；依据 [Lighter 官方 Core concepts](https://apidocs.lighter.xyz/docs/core-concepts#integer-prices-and-sizes)，其最小规模限制适用于 maker。开仓仍保留原有规模限制，其他交易所未声明减仓例外时继续按原规则检查。例如 ETH 平仓计划两腿各 0.0061，实际一腿平掉 0.0061、另一腿仅平掉 0.0055，则对剩余 0.0006 单独发送 reduce-only 修正，确认成交后继续运行；重启旧 pending 状态时也使用这套规模规则，核验无挂单与仓位稳定后再修正。

Arcus 的上层恢复、运行中修正和平仓计划也与其 `_place_request` 校验保持一致：reduce-only 免最小名义金额检查，不套用配置的开仓最小金额，但仍保留 `minOrderSize`、数量步长及单笔金额上限。例如 Arcus -0.4883306、另一腿 +0.4759 时，按 Arcus 自身精度修正多出的 0.0124306，不必平掉已配对部分。若确实因规模或单笔上限无法修正，启动日志会输出 `[BPS RECOVERY BLOCKED]`，包括交易所、净差额、按上限可下数量、避免小尾仓后的拟下数量、保护价、减仓最小数量/金额和单笔上限；保留 pending，不靠扩大敞口容差绕过。

RH/Lighter 挂单查询与撤单查询共享 REST 查询节流，失败后退避 2–8 秒，期间仍立即处理账户 WS 确认的成交。吃单 WS 回报超时、没有 WS 等待通道或提交连接异常时，额外用原 clientOrderIndex 查询 REST/WS 最终状态，最多复核约 10 秒，不重发可能已被接受的订单；必须得到有效终态与累计成交量后才处理差额。仍不能确认时保留 pending 并阻止新订单。REST 仓位与本地确认成交不一致时，持有交易锁并间隔 0.5 秒再次读取；短暂滞后不覆盖成交账本，持续变化或查询失败时等待复核，持续确认的异常变化仍暂停并保留待核对状态。

暂停原因分开记录：订单结果未确认、实时仓位尚未核实、修正订单提交失败、成交已确认但剩余差额未消除。暂时不可交易的已确认差额显示自动修正等待；无法安全修正的差额会显示实际净数量、名义敞口及具体交易所的减仓数量/金额限制，并输出 `[BPS PAUSED]`，监控摘要与周期 status 沿用这个原因。`[HEDGE BLOCKED]` 明确列出数量不足、金额不足、行情连接不可用或订单锁占用，不再统一声称“低于最小规模、下次重试”。

RH/LIGHTER 发单被明确的 HTTP 429 或 API 23000 限流拒绝时，按未被接受、零成交处理，不查询不存在的订单，也不因该拒绝把整轮记为结果未知。该腿进入至少 60 秒、且不短于服务端数字 `Retry-After` 的冷却；冷却期间不继续发该腿订单，结束后先刷新 nonce，再重新评估当前点位。没有差额时不进入永久 HALTED；另一腿已成交时，先 reduce-only 修正实际差额。若修正单本身被明确限流拒绝，则保持 pending、暂不发送新策略订单，等待冷却后继续有限修正；只有一个修正流程可以等待和发送，周期仓位核对不能另起重复修正。仍未知的原始提交、状态查询返回 429、或无法确认的网络异常不适用零成交判定，继续查询/保护。依据 [官方限流说明](https://apidocs.lighter.xyz/docs/rate-limits)，限流存在 L1 地址级共享限制，独立 API 密钥不等于独立额度；并行任务的合计流量仍可能再次触发限流，本变更未增加跨进程统一请求预算。

不同交易所的部分成交精度可能不同。对已确认成交留下的尾差，默认同时满足以下条件才只告警、继续按 BPS 点位交易：净数量不超过一个公共下单步长、以双腿最新有效行情中较高的中间价估算的名义敞口不超过 $0.10、剩余差额无法按正常步长及最小规模单独减仓。优先修正能下单的差额，不把交易所断线当作无法下单的精度尾差。上限可在 YAML 设置 `bps.max_dust_notional_usd`，默认 `0.10`，设为 `0` 关闭此规则。该金额是允许保留的名义敞口，不是亏损或滑点阈值；不改变开平仓点位。

例如 RH 买入 0.0647 SPY、Arcus 仅卖出 0.0249306，修正 RH 卖出 0.0397 后，净尾差为 +0.0000694 SPY；按约 $772 估值，名义敞口约 $0.054。符合上述条件时日志显示 `[BPS DUST]`，监控摘要显示精确数量和金额，两腿真实持仓、成本及状态文件仍保留原值。平仓时只处理可下单部分，无法单独下单的微小尾仓继续记录，不宣告整轮已全部平仓，不补算最终盈利；之后允许在当前点位、加仓间隔及持仓上限内继续交易。不会为了受单笔金额或深度限制的批次故意留下小尾仓。数量积累或价格变化导致超过上限时，暂停新机会并按实际差额尝试减仓或核验补齐；无法安全下单时保留保护。订单、对冲或外部仓位变化未确认时，不能靠小金额解除保护。

点位模式只按配置的价差点位判断，不增加最低盈利门槛。买卖价差已计入新口径，手续费另计，不会改变配置点位，但仍影响实际收益。`execution.leg_slippage_bps` 和 `hedge_slippage_bps` 继续作为真实订单的价格保护；不因取消估算而扩大滑点容忍。旧 YAML 的 `bps.cost_buffer_bps` 为兼容保留解析，但不再生效，网页已移除该字段。

该策略没有额外止损或强制最长持仓时间；溢价没有回到平仓点位时继续持仓。停止/暂停程序不会自动平仓。每天 8 点的旧三个套利阈值更新会跳过 bps 策略，不会替换这些点位或重启其持仓周期。

## 重启和日志

日志显示 `[BPS LEVELS]`（来源、窗口及点位）、`[BPS bps_open]`、`[BPS bps_close]`，交易记录的方向带 `bps_open:` 或 `bps_close:`。网页监控摘要显示当前点位、批次和等待/拦截原因。

网页「交易信号」同时支持 bps 策略与套利阈值策略，仅展示状态，不参与订单判断。可成交溢价按卖腿最优报价除以买腿最优报价计算；挂单开仓使用主腿买一/卖一挂单报价，平仓始终使用吃单报价。它不代表整笔订单的实际成交溢价。

bps 模式另列「触发指标」：executable 使用对应方向的可成交价差，两个比较符号都为 ≥；mid 旧口径使用中间价溢价。门槛为本轮锁定点位，页面显示实际生效口径。`≤` 条件的 gap 为「门槛 − 触发指标」，`≥` 条件的 gap 为「触发指标 − 门槛」，非负表示达到点位。尚未持仓时平仓行仅作参考。阈值模式的触发指标就是可成交溢价，门槛包含方向阈值、配置手续费与仓位附加值，gap 为可成交溢价减门槛。两种模式均不把 gap 当作净利润，达到点位也不意味着盘口深度、仓位限制等其他交易条件已经满足。

`logging.file` 对应目录中保存 `.bps-state.json`，包括本轮固定点位、批次、最后已确认的仓位及未确认主腿挂单标识。正常重启在市场和账户一致时恢复；若实际配对数量与旧记录不同，先核验两次无挂单且实时仓位稳定，归档旧记录并按当前配对持仓接管，历史成本标为未知。旧 `pending` 状态先走下述核验和修正流程。无法核验的归属、订单或仓位变化仍拒绝启动或暂停，不猜测归属，不自动反向加仓。

若上一轮留下 `pending=true`，启动时先验证账户和交易对归属。如果保存了旧主腿挂单标识，只查询并撤销这笔程序自己的挂单，等待成交/撤销终态；不批量撤销账户中的其他订单。旧版无挂单标识的状态只能在两次市场挂单查询均为空后恢复。间隔 5 秒复查两边挂单及仓位，仓位必须稳定。两边归零时直接解除旧状态；仍有持仓时，方向必须符合策略配置，启动行情和账户流后，优先用 reduce-only 减少多余一侧；规模不足时使用上述核验补齐路径，不平掉已有配对仓位。修正遵守单笔上限、最小规模及滑点保护，最多三笔，并避免留下无法交易的小尾仓。经最新行情确认属于上述精度尾差时，不发送无法成交的修正单；仍需再次通过两次无挂单及实时仓位核验，才解除 pending、启动正常策略。正常重启时若状态中也带有精度尾差，同样先核验并等待行情；已知成本与实际仓位匹配时保留成本记录。修正成交或仓位未确认时停止，不重复补单。

原文件归档为 `*.bps-state.json.recovered-<时间戳>.bak`，分钟行情和成交 CSV 保留。历史不确定成交的成本保持未知，不补算旧轮盈利；剩余仓位保留原点位，点位缺失时按手动配置或等待滚动历史。账户不匹配、方向不同、其他挂单、查询失败、仓位持续变化或差额无法安全下单时，保留 `pending` 并拒绝启动。日志中的 `[BPS RECOVERY]` 显示进度和结果，无须手工删除状态文件。

升级兼容：未指定 price_basis 的旧滚动点位模式自动采用 executable；为了保留原来选择的历史尾部，买主腿方向的开仓分位数 p 转为 100−p，卖主腿方向的平仓分位数 p 转为 100−p。例如旧 10/75 转为新 90/75。显式指定 executable 后直接按填写的分位数计算，不重复转换；网页同步时会写入显式口径与转换后的值。已有配对持仓的状态记录没有口径字段时，将其旧 mid 点位归档并直接切换当前配置口径，重新计算点位后即可交易，不必先平仓。旧 `exit_mode: profit` 配置兼容迁移为 `levels`，保留原口径、点位和仓位；未显式配置口径的旧净收益任务保留 mid。旧止盈、止损、最长持仓、开仓收益校验、额外滑点预算及冷却参数不再生效，页面保存时移除这些字段。成交成本和损益仍记录，但不参与 BPS 信号判断。

网页允许不同币种任务共用签名密钥，启动时只在页面和操作事件中提示 nonce 冲突及交易所限流风险，不要求再次确认。同一持仓市场的重复实盘管理、行情 CSV 和运行日志路径冲突仍拦截。RH/LIGHTER API 明确返回 invalid nonce 拒绝时，如果当前 SDK 支持异步 nonce 刷新，会刷新后按相同方向、数量、价格保护和 reduce-only 标识重试一次；再次失败则返回真实失败，不无限重试。依据 [官方安全重试规则](https://apidocs.lighter.xyz/docs/core-concepts#retrying-safely)，已接受但结果未知的订单只查原单，不走这条重新签名路径。此变更不提供跨进程 nonce 协调。


## RH / LIGHTER 账户查询与限流

所有同机、同系统用户的 RH / Lighter 策略、公开账户监控和市场监控，现在按 API 部署共用请求协调器。RH 与主网预算独立；同部署不同 API Key、不同币种不会获得独立额度。默认采用保守的部署合计 60 次 / 滚动 60 秒上限，覆盖后台 REST、当前 SDK 发单/撤单、订单查询和 nonce 读取。普通后台查询只使用前 36 个名额；普通新订单可用到第 48 个；订单确认、减仓、补对冲等关键请求最多使用总量 60。预留额度不是额外额度，不能保证在服务端已限流时仍能撤单或对冲。不同钱包也先共用这个保守上限，不自动切换收费账户或提高额度。SDK 初始化中的原生凭据检查保守预留两个请求名额；WebSocket 握手另用 120 次/分钟本机预算，握手收到 429 后也共享冷却。该握手预算不代替交易所的订阅、消息和在线连接数限制。

已有 signer 的策略 REST 查询使用现有 Key 本地生成的短期 Authorization 令牌，约 8 分钟续签一次，不需要新增 Key。认证失败不自动回退为公共查询；401/403 会清掉本地令牌以便下次重新生成。纯采集与公开账户监控不加载交易私钥，仍使用公共查询，但与策略共用本机预算、缓存和冷却。认证只改变适用的限流范围，不增加钱包总额度。平台规则参考 [官方限流文档](https://apidocs.lighter.xyz/docs/rate-limits)；本机 60 的保守设置不是对 RH 全部接口配额的断言，也不保证其他来源请求存在时不会遇到 429。

普通周期对账与余额展示共享最多 15 秒内的整账户响应，多个币种各取自己的仓位；账户编号与请求参数仍参与缓存键，不同账户数据不混用。启动、旧仓接管、成交后/异常仓位核验只复用 200 ms 内的响应，间隔 0.5 秒的复核会重新请求。提交订单会使共享账户缓存失效；快照早于本腿最后成交时间时也不使用。无效化不等待慢查询，慢查询的旧响应不能重新成为有效缓存。订单确认和提交均不缓存，实际盘口继续取实时 WebSocket。

HTTP 429、405 或明确的查询/SDK code 23000 后，相同部署共享至少 60 秒冷却，并遵循更长的 Retry-After。本机预算不足只推迟请求，不向交易所发起请求，也不凭空刷新 nonce。策略在提交前快速检查预算，提交时原子占位；不会排队保存旧盘口计划后再发单。已在途的请求仍可能完成，不因一次请求被拒绝而猜测其他订单为零成交。未知提交仍只核验原订单，不重新发送。

冷却或预算等待期间保留最后确认的仓位和余额；仓位未核验时所有策略模式均阻止新交易，恢复后重新核验。不把查询限流累计为交易所断线。市场加载、签名初始化预算与启动仓位核验各阶段最多尝试三次、单阶段最多等待 180 秒，等待可被停止操作打断；未确认启动仓位前不发交易订单。超过重试范围保留明确原因退出，不无限重试。

协调文件位于系统临时目录 `entropy-arb-rest-<uid>`（目录 700、文件 600），不存签名私钥或认证令牌。不要在运行中删除目录，否则会重置本机计数。进程重启继续使用同一目录。不同服务器、不同系统用户或使用不同临时目录的进程不会自动协调，同 IP 的这些额外来源仍可能触发平台限流；需要统一运行用户或部署外部集中协调服务。`ENTROPY_REST_DIR` 可指定本用户私有且所有进程一致的目录，不应放到其他用户可写目录。

日志标识包括 `[REQUEST POLICY]`、`[REQUEST BUDGET]`、`[REQUEST COOLDOWN]`、`[REQUEST 429]` 和 `[STARTUP QUERY WAIT]`。429 记录接口、是否认证、数值错误码及依据服务端消息得出的 scope_hint，不输出令牌、完整请求头或错误回显。scope_hint=unknown 时不凭 CloudFront 响应头猜测规则。`status.json` 各交易所的 `request_budget` 提供本进程协调调用/缓存命中次数、共享已占用名额及冷却时间，不是交易所精确计费账单。

`max_orders_per_min` 仍是每个策略每条腿的附加下单预算，不能代替共享请求控制。需要停止并重启全部旧策略和网页监控进程后，新预算才能覆盖它们；只 git pull 不会更新已有进程。重启程序不自动平仓，保留现有仓位与状态文件，按原规则核验接管。
